# Gateway VPN — проектные инструкции Codex

## Непрерывность разработки

- Зафиксированный архитектурный контракт находится в `docs/PLAN_v1.1.md`.
- Фактический ход, результаты проверок, неудачи, ограничения и следующий шаг ведутся в `docs/PROJECT_STATUS.md`.
- После побочного вопроса продолжать с последнего незавершённого шага журнала, не перезапуская уже завершённую работу.

## Одноразовые ресурсы разработки

- Не удалять автоматически Docker containers, images, volumes, networks, build cache, project `.cache`, validation bundles или lifecycle-стенды после тестов.
- Можно сообщать пользователю фактический размер и потенциально освобождаемое место, но cleanup, prune, удаление cache и сжатие Docker VHDX выполнять только после отдельного явного запроса пользователя.
- `open-webui`, его image и volume всегда сохранять, если пользователь явно не распорядился иначе.
- Проектные кэши, временные файлы и результаты тестов хранить внутри папки проекта; `%TEMP%`, профили пользователя и другие системные каталоги не использовать для Gateway VPN без отдельного согласования. Если внешний временный путь всё же необходим для диагностики, его назначение и последующее удаление явно фиксируются в журнале.

## Протокол уровня мышления

- Штатный уровень для разработки проекта — **High / Высокий**.
- Фактическим считается последний уровень, переключение на который пользователь явно подтвердил. Сообщение Codex о том, что уровень можно или нужно изменить, само по себе уровень не меняет.
- Перед любым переходом уровня — как повышением, так и понижением — остановить работу, сообщить требуемый уровень и краткую техническую причину и дождаться явного подтверждения пользователя. До подтверждения не начинать следующий блок и не продолжать проектную работу.
- До начала блока, для которого ради качества существенно нужен **xhigh / Очень высокий**, **max / Макс** или **ultra / Ультра**, применить этот протокол остановки и подтверждения.
- Повышение обычно требуется для критических сквозных изменений в `nftables`, policy routing, WireGuard, systemd/root boundary, release signing, zero-to-ready installers, recovery/rollback, миграциях данных, сложной диагностике и финальном security/release audit. Решение принимать по фактической сложности, а не только по названию компонента.
- **Ultra / Ультра** запрашивать только для особо сложной работы, которая действительно делится на несколько независимых исследовательских, реализационных или проверочных потоков и получает пользу от их параллельного выполнения; перед использованием отдельно дождаться явного подтверждения пользователя.
- Как только повышенный уровень больше не нужен, перед обычной работой предложить возврат на **High / Высокий**, остановиться и дождаться явного подтверждения переключения. Если пользователь не подтвердил возврат, фактический повышенный уровень сохраняется.
- Для документации, журнала, механических правок и простых изолированных тестов не запрашивать повышение без конкретной причины.
- Уровень мышления не заменяет тесты и реальные Linux/hardware gates; не ослаблять критерии проверки при любом уровне.
